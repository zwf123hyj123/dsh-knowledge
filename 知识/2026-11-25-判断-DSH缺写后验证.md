# 判断：DSH 的问题不是功能缺失，是缺「写后验证」这一层

> 一句话：**DSH 把「执行」当成了「生效」。**
> 这是根因判断，不是事实陈述——证据如下，可被引用、可被反驳。

## 证据（2026-11-25 实测）

| 以为发生 | 实际发生 | 缺的环节 |
|---|---|---|
| 改了 settings.json，配置生效 | 插件启动时 flush，覆盖回原样 | 写后没读回 |
| 热重启完成，服务恢复 | 本地 Ollama 被连带杀掉 | 重启后没查依赖 |
| 检测器报「配对正常」 | 检测器自己读错字段（0 result） | 判据没自检 |
| 会话恢复 | 工具注册表 48→19 | 恢复后没比对清单 |

## 为什么大团队不修

不是想不到，是不划算：
- 写后验证会让每次写多一次读回，拖慢海量用户的体验
- DSH 的架构选择「信任模型、让 agent 自己验证」，验证责任下放
- 对 100 万用户，「轻」比「确定」重要；对单机长任务，反过来

## 可连接的方向（谁能直接用）

1. **写配置的插件作者**：用 `state_guard.atomic_write`（写前备份→临时→读回→原子替换）
2. **做压缩的**：压完抽关键 token 核对（我们用的是「工具名 + 百分比」，误报低）
3. **做重启/切换的**：切完查依赖（Ollama、网关），不能只看主端口
4. **做检测器的**：先自检判据（我们的第一次扫描全报 0，就是判据错了）

## 反证条件（什么情况下这条判断不成立）

- 如果官方后续版本引入了统一的写入校验层 → 这条判断过时
- 如果「模型自己验证」在更强模型下真的可靠 → 这条判断的价值下降
- 如果写后验证的性能代价在手机上不可接受（我们实测：几毫秒，可接受）→ 需要重新权衡
